## 保留的失败现场与原因定位

文档产物流直接从 Markdown 中提取 Python 代码块执行，没有重写其断言。失败现场保留在：

```text
C:\Users\1\AppData\Local\Temp\ai-image-windows-hq9evtk1
  source.png                         6796 bytes
  中文 空格\slide.png                6758 bytes
  中文 空格\raw\slide.png格          6796 bytes
```

实际 raw 文件名多出了 `格`（U+683C），因此契约要求的 `raw/slide.png` 不存在。现场未做重命名或清理。该流程在首次 raw 字节校验处中止；候选版本的后续覆盖、editable 与导出链路没有被这个流程验证通过。

重点代码是 [`scripts/windows_image_output.py`](../../scripts/windows_image_output.py) 的 `_NativeApi.rename`（被测版本第 299 行起）：第 304 行只分配 `offset + len(encoded)` 字节，再完整填入 UTF-16 路径，没有为结尾 NUL WCHAR 留出空间。后续发布返回对象以打开句柄的身份为依据，当前用例暴露出“报告成功但预期路径缺失”的结果。

微软 [FILE_RENAME_INFO 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) 的 `FileName` 描述要求 NUL-terminated wide string，而 `FileNameLength` 描述又称 terminating null 不必需。因此这里的原因判断以 Windows 实测对照为依据，不仅依赖文档措辞。

## 进程内对照实验（不是修复交付）

诊断脚本只在自身进程中替换 `_NativeApi.rename`，保持 FileNameLength、句柄、共享规则和不覆盖语义不变，唯一行为差异是将分配大小改为 `offset + len(encoded) + 2`，使最后一个 UTF-16 WCHAR 保持零值。

- 24 项原生模块测试加 1 项 host 导入测试：**25/25 通过**，0.344 秒。
- 随后原样执行文档产物流：**通过**，包括 raw 保留、首次拒绝覆盖、显式替换、1664×936 主图、1280×720 editable 输入、单页 16:9 PPTX 重开及非空 PDF。
- 对照产物：`C:\Users\1\AppData\Local\Temp\ai-image-windows-zgjvae4_\中文 空格`。
- 进程退出后替换失效，候选源码未改变。后续在新进程执行原始测试仍报错。

建议修复时显式提供 NUL 结尾缓冲区，并增加覆盖多种长度和中文/空格路径的真实 Win32 回归，验证句柄最终路径与约定目标一致；然后重新执行完整 Windows 门禁和文档产物流。当前证据不足以宣告修复完成。
